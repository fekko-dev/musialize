# Passwordless sign-in with email codes and invite links

Research date: 2026-11-06. Sources are Microsoft Learn (ASP.NET Core 10 docs), the `dotnet/aspnetcore` and `dotnet/runtime` source on the `release/10.0` branches, the OWASP Cheat Sheet Series, NIST SP 800-63B-4, RFC 10017, the W3C Referrer Policy spec, and the vendors' own pricing, docs and security pages. Points that a source does not state, or that I inferred, are marked ⚠️.

Context: an Account signs in by entering an email address and then a one-time code sent to it. There are no passwords. A Group admin shares the Group's invite link, and a person uses it to Claim an Unclaimed Member ([ADR 0003](../adr/0003-members-without-accounts.md)). One deployment serves several Groups, and one Account can be linked to Members of several Groups ([ADR 0002](../adr/0002-multiple-groups-per-deployment.md)). Mail goes out through Lettermint over SMTP ([ADR 0006](../adr/0006-lettermint-smtp-for-transactional-email.md)), and sending it is out of scope here. The SPA and the API share one origin on a subdomain of `fekko.dev`. The target is .NET 10. Passkeys come later and must not be blocked.

## 1. Summary and recommendation

**Build it ourselves on plain cookie authentication (`AddCookie`), with three small tables of our own: Account, sign-in code, and Group invite. Don't use ASP.NET Core Identity, an identity server, or a hosted provider for the pilot.**

1. **It is the least code for this flow.** Identity's built-in email code is a TOTP derived from the security stamp. It isn't single-use, it stays valid for 6–9 minutes, and it reads the system clock directly (§2.1). So we would build our own code table even on top of Identity. `MapIdentityApi` is built around passwords (`/register`, `/login`, `/forgotPassword`), so its endpoints don't help either ([Identity for SPAs](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0#the-mapidentityapituser-endpoints)). What's left is one sign-in call, `HttpContext.SignInAsync`, which plain cookie auth already gives us ([cookie auth without Identity](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0#create-an-authentication-cookie)).
2. **Cookie sessions fit a same-origin SPA.** Microsoft recommends cookies for browser apps ([Identity for SPAs](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0#use-token-based-authentication)). RFC 10017 §7.1 says single-domain apps should use server-side cookie sessions rather than OAuth. SignalR picks up the cookie with no extra setup (§3).
3. **Buying doesn't remove the work that is specific to Musialize.** The Group invite link, Claims and Account↔Member links stay in our database whichever provider we pick. A provider only replaces the code-and-cookie part, which is about a day of work. In exchange it adds an OIDC integration, a second place where user data lives, and (for Clerk) US hosting (§2).
4. **Passkeys stay open.** .NET 10 Identity ships passkeys behind `SignInManager`/`UserManager<TUser>`, and the store is pluggable (`IUserPasskeyStore<TUser>`). Later we can either put `UserManager<Account>` over our own Account table with a small custom store, or move Account onto `IdentityUser`. ⚠️ I haven't checked the minimum set of store interfaces `SignInManager` needs for `PasskeySignInAsync`.

**Trade-offs we accept.** We own about 300–400 lines of security code. That makes the checklist in §4 mandatory, not optional. NIST 800-63B-4 says "Email **SHALL NOT** be used for out-of-band authentication" (§3.1.3.1), so email codes are not a NIST-recognised authenticator at any AAL. For a trusted group of musicians with a Group admin who can undo Claims, that is acceptable. Passkeys are the upgrade path.

**Runner-up:** Identity Core (`AddIdentityCore<Account>().AddEntityFrameworkStores().AddSignInManager()`) with our own code table. Choose it instead if passkeys are planned within a few months: passkeys then become a schema bump (`IdentitySchemaVersions.Version3`) plus four endpoints. The price is an `AspNetUsers`-style table with columns we don't use, and Identity's model of users and usernames sitting next to our Account/Member split.

### 2.1 (a) ASP.NET Core Identity

- **No password is needed.** `IdentityUser.PasswordHash` is nullable, and `UserManager.CreateAsync(TUser user)` has an overload without a password ([IdentityUser.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/Extensions.Stores/src/IdentityUser.cs), [UserManager.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/Extensions.Core/src/UserManager.cs)). The user table still carries `PasswordHash`, `PhoneNumber`, `TwoFactorEnabled`, `LockoutEnd`, `AccessFailedCount` and so on.
- **Email token provider.** `EmailTokenProvider` derives from `TotpSecurityStampBasedTokenProvider` and formats a 6-digit code (`"D6"`) ([TotpSecurityStampBasedTokenProvider.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/Extensions.Core/src/TotpSecurityStampBasedTokenProvider.cs)). `Rfc6238AuthenticationService` uses a 3-minute timestep and accepts steps −2…+2 ("variance of no greater than 9 minutes"). It reads `DateTimeOffset.UtcNow` directly ([Rfc6238AuthenticationService.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/Extensions.Core/src/Rfc6238AuthenticationService.cs)). So a code is accepted 6–9 minutes after issue, and **more than once**, until the security stamp changes. The only way to make it single-use is to rotate the stamp, which also ends every other session through `SecurityStampValidator`. OWASP and NIST both require single use (§4.1), so we would need our own table anyway.
- **Passkeys (.NET 10).** "ASP.NET Core Identity includes built-in support for passkey registration and authentication", covering passwordless account creation and passwordless sign-in. The listed limitations are "Only the Blazor Web App template includes passkey support", no attestation validation by default, and "Passkeys are treated as a primary authentication factor, not as a second factor" ([Enable WebAuthn passkeys](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0)). The APIs are `SignInManager.MakePasskeyCreationOptionsAsync`, `PerformPasskeyAttestationAsync`, `MakePasskeyRequestOptionsAsync`, `PasskeySignInAsync` and `UserManager.AddOrUpdatePasskeyAsync`. Storage goes through `IUserPasskeyStore<TUser>`, and the EF store adds a passkeys table when `Stores.SchemaVersion = IdentitySchemaVersions.Version3` ([IUserPasskeyStore.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/Extensions.Core/src/IUserPasskeyStore.cs), [IdentityUserContext.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/EntityFrameworkCore/src/IdentityUserContext.cs), [Blazor template Program.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/ProjectTemplates/Web.ProjectTemplates/content/BlazorWeb-CSharp/BlazorWebCSharp.1/Program.cs)). `PasskeyHandler<TUser>` takes a `UserManager<TUser>` in its constructor ([PasskeyHandler.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Identity/Core/src/PasskeyHandler.cs)), so the passkey support is tied to Identity's `UserManager`, though not to Identity's EF schema. The docs also warn: set `IdentityPasskeyOptions.ServerDomain` rather than inferring it from the Host header, and "Don't serve untrusted content on any subdomain" of it ([Enable WebAuthn passkeys: Security considerations](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0#security-considerations)).

### 2.2 (b) Custom minimal

- Microsoft documents this path as "Use cookie authentication without ASP.NET Core Identity": `AddAuthentication().AddCookie()`, then `HttpContext.SignInAsync` with a `ClaimsPrincipal`. The cookie is encrypted with Data Protection ([cookie auth](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0)).
- Tables (⚠️ my design):
  - `Account(Id, Email, NormalizedEmail unique, CreatedAt)`
  - `SignInCode(Id, NormalizedEmail, CodeHash, CreatedAt, ExpiresAt, FailedAttempts, ConsumedAt)`
  - `GroupInvite(Id, GroupId, TokenHash unique, CreatedByMemberId, CreatedAt, ExpiresAt?, RevokedAt?)`

  Member gets a nullable `AccountId`.

- Endpoints: `POST /api/auth/code` (request), `POST /api/auth/verify`, `POST /api/auth/sign-out`, `GET /api/me`, `POST /api/invites/resolve`, `POST /api/invites/claim`.
- Put only the Account ID in the cookie. Check Group membership and Group admin rights against the database on every request and hub call, so an undone Claim takes effect immediately (§3.3).

### 2.3 (c) Keycloak

- Passkeys: "Passkeys integration (supported)" in 26.4.0, enabled per realm in the WebAuthn Passwordless Policy ([release notes](https://www.keycloak.org/docs/latest/release_notes/index.html), [passkeys in 26.4](https://www.keycloak.org/2025/09/passkeys-support-26-4)). The latest release is 26.8.x.
- Email OTP and magic links: no entry in the release notes and no mention in the passkeys post. The email-code authenticator I found is a third-party extension that runs as a 2FA step ([keycloak-2fa-email-authenticator](https://github.com/mesutpiskin/keycloak-2fa-email-authenticator/releases/tag/v26.7.0)). ⚠️ The release-notes page is long and I could only scan part of it, but nothing points to a core feature.
- Ops: "The `dev-file` database is not suitable for production use-cases", so it needs its own production database ([Configuring the database](https://www.keycloak.org/server/db)). That means another service to upgrade, back up and theme before a deadline. Not worth it for one Group.

### 2.4 (d) Hosted providers

- **Auth0.** Free covers 25,000 MAU and includes passwordless and passkeys. Essentials (B2C) costs $35/month ([pricing](https://auth0.com/pricing)). Tenant "localities … control the assigned tenant domain and the region where your data will be hosted", with Europe listed as EU / EU-2 ([tenants](https://auth0.com/docs/get-started/auth0-overview/create-tenants)). ⚠️ Neither page says whether region choice is limited by plan. The built-in email provider is for testing only, so production needs our own SMTP provider configured in Auth0 ([customize email](https://auth0.com/docs/customize/email), [email OTP](https://auth0.com/docs/connections/passwordless/guides/email-otp)). That would mean Lettermint, configured twice.
- **Clerk.** Hobby covers 50,000 MRU per app and includes the email code. Passkeys need Pro at $25/mo, or $20/mo billed annually ([pricing](https://clerk.com/pricing)). "Clerk does not offer regional data residency or region selection. Data is hosted on US infrastructure" ([security](https://clerk.com/security)). That rules it out if EU residency matters, as it did for the email provider.
- **Zitadel Cloud (EU option).** Free covers 100 DAU and lists "Data Residency: EU, US, Switzerland, Australia". Pro costs $100/month ([pricing](https://zitadel.com/pricing)). The docs describe email OTP as an MFA check (`otpEmail`) that needs "a session with a checked user" ([MFA in a custom login UI](https://zitadel.com/docs/guides/integrate/login-ui/mfa)). ⚠️ Email code as the only factor is not documented. It looks possible through a custom login UI on the Session API, which is more work, not less.
- **For every hosted option** the SPA needs an OIDC redirect flow. The backend then either becomes a BFF that exchanges the code and issues its own cookie (RFC 10017 §6.1), or it validates bearer tokens and SignalR has to take `access_token` from the query string (§3.2). Either way we keep a local Account table keyed on the provider's subject, plus all the invite and Claim logic.

## 3. Session mechanism and SignalR

### 3.1 What the primary sources say

- **Microsoft:** "We recommend using cookies in browser-based applications, because, by default, the browser automatically handles them without exposing them to JavaScript." Identity's own bearer tokens "aren't standard JSON Web Tokens" and are meant for "clients that can't use cookies" ([Identity for SPAs](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0#use-token-based-authentication)).
- **OWASP:** don't store auth tokens, session IDs or JWTs in `localStorage` or `sessionStorage`. Use `HttpOnly; Secure; SameSite=Strict` cookies, or a BFF that keeps tokens on the server ([Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)).
- **RFC 10017 (BCP 212, August 2026, formerly `draft-ietf-oauth-browser-based-apps`):**
  - §7.1, "Single-Domain Browser-Based Applications (Not Using OAuth)": "Too often, simple applications are made needlessly complex by using OAuth to replace the concept of session management." It recommends server-side, cookie-based session state using the cookie rules in §6.1.3.2: `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`, and the `__Host-` prefix.
  - §6.1 BFF is the most secure of the OAuth patterns, but it only matters when an external OAuth/OIDC provider is involved ([RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)).

**Conclusion for Musialize:** a cookie session issued by our own API. With no external IdP there is nothing for a BFF to hold, so the API already plays that role. If we ever add a hosted IdP, the API becomes a BFF and keeps issuing the same cookie, and the SPA doesn't change.

### 3.2 SignalR

- **Cookies:** "In a browser-based app, cookie authentication allows existing user credentials to automatically flow to SignalR connections … no extra configuration is needed" ([SignalR authn/authz: Cookie authentication](https://learn.microsoft.com/en-us/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#cookie-authentication)). Since ASP.NET Core 10, SignalR endpoints get a 401/403 instead of a login redirect when unauthenticated ([what's new in 10](https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0)).
- **Bearer tokens:** "browsers can't set custom headers, such as `Authorization`, on the WebSocket and Server-Sent Events APIs", so the client sends `access_token` in the query string, and the server has to read it in `OnMessageReceived` ([SignalR authn/authz: Bearer token authentication](https://learn.microsoft.com/en-us/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#bearer-token-authentication)). "ASP.NET Core logs the URL for each request by default, which includes the query string", so tokens end up in logs unless `Microsoft.AspNetCore.Hosting` logging is raised to `Warning` or filtered ([SignalR security: Access token logging](https://learn.microsoft.com/en-us/aspnet/core/signalr/security?view=aspnetcore-10.0#access-token-logging)).
- **Expiry:** "If a token expires during the lifetime of a connection, by default the connection continues to work." `CloseOnAuthenticationExpiration` closes it instead. Refreshing authentication without reconnecting is ".NET 11 and later" ([SignalR authn/authz: Authentication refresh](https://learn.microsoft.com/en-us/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#authentication-refresh)). ⚠️ The docs show `CloseOnAuthenticationExpiration` for bearer tokens. I didn't verify its behaviour with a cookie's `ExpiresUtc`.
- **Cached principal:** "SignalR captures the authenticated user when a connection is established and caches it for the lifetime of the connection" (same page, "User and role changes during the connection lifetime"). Another reason to keep Group and Group admin facts out of claims and check them in the database.
- **CORS doesn't cover WebSockets:** "The protections provided by CORS don't apply to WebSockets" ([SignalR security](https://learn.microsoft.com/en-us/aspnet/core/signalr/security?view=aspnetcore-10.0#websocket-origin-restriction)). The origin check in §4.3 covers this.

### 3.3 Session lifetime

- NIST AAL1: "A definite reauthentication overall timeout **SHALL** be established, which **SHOULD** be no more than 30 days." An inactivity timeout "is not required at AAL1" ([SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)).
- OWASP suggests idle timeouts of 15–30 minutes for low-risk apps and an absolute timeout ([Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). These two sources conflict for this kind of app (§6).
- Cookie handler defaults are `ExpireTimeSpan = 14 days` and `SlidingExpiration = true` ([CookieAuthenticationOptions.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Security/Authentication/Cookies/src/CookieAuthenticationOptions.cs)). With sliding expiration, a weekly visitor never has to sign in again, so there is no overall timeout.
- **Recommendation:** a persistent cookie with a fixed 30-day lifetime, set through `IsPersistent = true` and `ExpiresUtc` at sign-in, and `SlidingExpiration = false`. That is about one code email per Account per month, roughly 40/month for the first Group, well inside Lettermint's 300/month free tier. It also answers ADR 0006's open question on volume. The cookie docs say persistence "should only be enabled with explicit user consent" via a "Remember me" box. [ADR 0007](../adr/0007-passwordless-sign-in-with-cookie-sessions.md) adds the checkbox.
- **Revocation (YAGNI for the pilot):** use `ValidatePrincipal` with a per-Account stamp to revoke single sessions. The docs warn that validating on every request costs performance ([cookie auth: React to back-end changes](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0#react-to-back-end-changes)). For the pilot, the emergency switch is to rotate the Data Protection keys, which invalidates every cookie.

## 4. Security requirements checklist

### 4.1 One-time sign-in codes

- [ ] **6 digits from a CSPRNG:** `RandomNumberGenerator.GetInt32(0, 1_000_000).ToString("D6")`. NIST requires "at least six decimal digits" from an approved random generator (SP 800-63B-4 §3.1.3.2 and §3.1.2.1). OWASP suggests "8-digit or longer codes where usability allows" ([MFA CS: One-time codes](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)). 6 digits plus the attempt limits below is enough. ⚠️ judgement.
- [ ] **Expiry ≤ 10 minutes**, enforced on the server through `TimeProvider`: "the authentication **SHALL** be considered invalid unless completed within 10 minutes" (SP 800-63B-4 §3.1.3.2).
- [ ] **Single use:** mark the code consumed with a conditional update (`… WHERE ConsumedAt IS NULL`) so two concurrent requests can't both succeed. NIST: accept a secret "only once during the validity period" (§3.1.3.2). OWASP: "Ensure OTPs are single use", "Invalidate the OTP on successful verification" (MFA CS).
- [ ] **A new code replaces the old one:** OWASP says to "generate a new OTP and overwrite the old record" (MFA CS).
- [ ] **At most 5 wrong guesses per code**, after which the code is dead. Also cap failures per email across codes, for example 20 in 24 hours, then refuse new codes for that email until the window passes. NIST §3.2.2: "limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account", with 100 as the upper bound. Failures must not reset when a new code is issued. With these limits an attacker's daily success chance is ≤ 20/10⁶. ⚠️ The numbers are my choice.
- [ ] **Store a keyed hash, not the code:** HMAC-SHA256 with a server-side key from configuration. Compare with `CryptographicOperations.FixedTimeEquals`. It "doesn't leak timing information" and only short-circuits on different lengths ([API docs](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.cryptographicoperations.fixedtimeequals?view=net-10.0)). ⚠️ NIST says nothing about storing OOB secrets. For look-up secrets under 112 bits it requires a salted password-hashing scheme (§3.1.2.2). A plain SHA-256 of a 6-digit code can be brute-forced instantly, so only a keyed hash makes hashing worth anything.
- [ ] **No account enumeration:** `POST /api/auth/code` always returns the same status and body. OWASP: respond generically and keep "consistent response times" ([Authentication CS: Authentication and Error Messages](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html); [Forgot Password CS](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)). The simplest way to get this is to make sign-in and sign-up the same flow: **always** send a code, and create the Account only on successful verification. Then there is no branch to time. An Account with no Member just sees "ask your Group admin for the invite link". ⚠️ design choice.
- [ ] **Rate-limit code requests** to protect inboxes and the 300 emails/month quota:
  - per normalized email: 1/minute and 5/hour, counted from `SignInCode` rows, so the limit survives restarts;
  - per IP: `AddRateLimiter` with a partitioned fixed window on `RemoteIpAddress` and `RequireRateLimiting` on the auth endpoints;
  - a small global cap.

  OWASP: per-account limits so attackers can't flood a user's inbox (Forgot Password CS). Microsoft: "If you create partitions by using user input, your app becomes vulnerable to Denial of Service". Limiter state is per instance and in memory. The docs show setting `RejectionStatusCode = StatusCodes.Status429TooManyRequests` explicitly ([rate limiting middleware](https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit?view=aspnetcore-10.0)). That is why the per-email limit lives in the database and not in a limiter partition.

- [ ] **Per-IP limits only work behind the proxy with forwarded headers.** Dokploy's proxy terminates TLS, so `RemoteIpAddress` and `Scheme` are the proxy's unless `UseForwardedHeaders` is configured with the proxy in `KnownProxies`/`KnownNetworks`. By default "Only loopback addresses are configured for known proxies and known networks" ([proxy and load balancer](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0)).
- [ ] **Renew the session on sign-in:** call `SignInAsync` fresh on every verification, and sign out first if another Account was signed in. OWASP: regenerate the session ID on privilege changes, including login (Session Management CS).
- [ ] **Never log codes,** and don't put them in URLs. The code is typed in, not linked.

### 4.2 Group invite links

- [ ] **Generate 256 bits:** `RandomNumberGenerator.GetBytes(32)`, encoded Base64Url. `RandomNumberGenerator.GetString`/`GetHexString` also work and exist since .NET 8 ([API docs](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator.getstring?view=net-10.0)). OWASP: CSPRNG tokens "long enough to resist brute-force" (Forgot Password CS). Session IDs need ≥ 64 bits, and custom ones should use 128 bits (Session Management CS).
- [ ] **Hash at rest with SHA-256 and look it up by hash.** With ≥ 112 bits of entropy, NIST does not require a salted password hash (SP 800-63B-4 §3.1.2.2, by analogy). ⚠️ Looking up by the hash of a high-entropy token leaks nothing useful through timing, so no constant-time compare is needed.
- [ ] **Reusable, revocable and rotatable, not single-use.** ADR 0003 defines one invite link per Group that anyone in the Group can use. That differs from OWASP's single-use reset tokens, which grant account access directly. The invite link grants no access: the person still proves their email with a code. So a Group admin can revoke it and create a new link, optionally with an expiry. ⚠️ judgement. A Claim stays correctable by a Group admin (ADR 0003).
- [ ] **Put the token in the URL fragment** (`/join#<token>`). The SPA reads it and POSTs it to `/api/invites/resolve`. Browsers never send fragments to the server, so they don't appear in proxy or Kestrel logs. The Referrer Policy spec strips them from `Referer` ("Set url's fragment to null", [Referrer Policy §8.4](https://w3c.github.io/webappsec-referrer-policy/)). Then call `history.replaceState` to remove it from the address bar. ⚠️ The fragment approach is my recommendation, not something a source prescribes.
- [ ] **Set `Referrer-Policy` explicitly:** `strict-origin-when-cross-origin` site-wide, as the OWASP HTTP Headers CS recommends ([HTTP Headers CS](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)), or `no-referrer` on token pages as the Forgot Password CS recommends.
- [ ] **Build links from configuration, not from the Host header:** OWASP warns against building token URLs from the Host header (Forgot Password CS: Host Header Injection).
- [ ] **Rate-limit `resolve`** per IP, like the code endpoints (Forgot Password CS: rate-limit token brute-forcing).
- [ ] **Already signed in:** skip the email step, because the session already proves the email. Show the Group's Unclaimed Members and Claim with a conditional update (`… WHERE AccountId IS NULL`), returning 409 if someone else got there first. If the Account already has a Member in that Group, show that Member instead of offering a second Claim. ⚠️ ADR 0003 says the Claim is "confirm[ed] … with an email code". This reads it as "the person has proven their email", which an existing session already shows. See the open questions.
- [ ] **Not signed in:** resolve → choose a name → enter email → code → verify, then Claim in the same request or straight after. Keep the chosen Member in the SPA state, not in a server-side pre-session.

### 4.3 Cookies, CSRF and CORS

- [ ] **Cookie settings:** name `__Host-musialize`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`, and `SecurePolicy = Always`. The default is `SameAsRequest` ([CookieAuthenticationOptions.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Security/Authentication/Cookies/src/CookieAuthenticationOptions.cs)), which would leave out `Secure` behind a TLS-terminating proxy. Sources: OWASP Session Management CS and RFC 10017 §6.1.3.2. ⚠️ `Strict` should not break the SPA: the HTML shell doesn't need the cookie, and the SPA's own `fetch` calls are same-site. The `__Host-` prefix matters here because sibling `*.fekko.dev` apps are _same-site_: it stops them setting or overwriting our cookie. OWASP calls naive double-submit "DISCOURAGED" for exactly this sibling-subdomain cookie injection ([CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)).
- [ ] **SameSite is not the CSRF defense:** "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense" (CSRF CS). Microsoft calls it "part of a defense-in-depth strategy" ([antiforgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0)). It also does nothing against other `*.fekko.dev` subdomains, which count as same-site.
- [ ] **Fetch Metadata + Origin check, as about 15 lines of middleware.** It runs on every non-GET/HEAD/OPTIONS request and on WebSocket upgrades:
  - allow if `Sec-Fetch-Site` is `same-origin` or `none`;
  - otherwise, if `Sec-Fetch-Site` is absent, allow only when `Origin` matches our own origin;
  - allow if both headers are absent (non-browser clients);
  - reject everything else with 403.

  OWASP lists Fetch Metadata as a defense, makes an Origin/Referer fallback "a mandatory requirement", and says not to treat `Origin: null` as same-origin (CSRF CS). These rules mirror the automatic CSRF middleware that ships in .NET 11 ([antiforgery, .NET 11](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-11.0)).

- [ ] **Login CSRF:** `POST /api/auth/verify` goes through the same check. OWASP: CSRF on login forms matters too (CSRF CS: Login CSRF).
- [ ] **No state changes on GET:** "SameSite=Lax cookies are still sent with top-level GET requests, meaning any state-changing GET endpoints remain vulnerable" ([antiforgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0)).
- [ ] **Antiforgery tokens (`IAntiforgery`) are not needed.** Minimal APIs validate them automatically only on form-bound POST/PUT/PATCH endpoints, so JSON endpoints would need manual `ValidateRequestAsync` calls ([antiforgery: minimal APIs](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0)). Fetch Metadata + Origin is a defense OWASP lists in its own right. ⚠️ judgement. Add tokens later only if we have to support browsers that send neither header.
- [ ] **No CORS policy in production.** SPA and API share scheme, host and port, which is the definition of same origin. CORS "is **not** a security feature, CORS relaxes security" ([CORS](https://learn.microsoft.com/en-us/aspnet/core/security/cors?view=aspnetcore-10.0)). SignalR only needs CORS when "JavaScript code is hosted on a different domain" ([SignalR security](https://learn.microsoft.com/en-us/aspnet/core/signalr/security?view=aspnetcore-10.0#cross-origin-resource-sharing)). For local dev, use Vite's dev-server proxy for `/api` and `/hubs` so dev is same-origin too. ⚠️ I didn't look up Vite's docs for this.
- [ ] **Persist Data Protection keys,** for example with `PersistKeysToDbContext` in Postgres, and set `SetApplicationName`. Otherwise every redeploy invalidates all cookies. "When hosting in a Docker container, keys should be maintained" in a persistent volume or store ([Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0#persisting-keys-when-hosting-in-a-docker-container)).

- **Tests worth writing:**
  - request → fake mail → verify → `GET /api/me` returns 200;
  - wrong code 5× kills the code;
  - `Advance(11 min)` makes the code expire;
  - a used code is rejected on reuse;
  - `Advance(31 days)` makes `/api/me` return 401;
  - the same response for known and unknown emails;
  - a `Sec-Fetch-Site: cross-site` POST is rejected with 403;
  - claim races return 409;
  - a revoked invite fails.

  Make rate-limit numbers configurable and set them high in tests, except in the one test that checks a limit. Those limits run on real time, so that test can't use `FakeTimeProvider`.

- **Fetch Metadata in tests:** `TestServer` requests carry neither `Sec-Fetch-Site` nor `Origin`, so they pass as non-browser clients. Add the headers explicitly in the negative tests.

## 6. Caveats / version notes

- **Target .NET 10 (LTS).** The latest .NET 11 release is `v11.0.0-rc2` (2026-10-13), not GA ([dotnet/core releases](https://github.com/dotnet/core/releases)). Three .NET 11 features would simplify this design, but don't build on them for the pilot:
  - the automatic CSRF middleware (`ICsrfProtection`, Fetch Metadata based);
  - SignalR authentication refresh;
  - `UserManager` honouring `TimeProvider`.
- **.NET 10 specifics:**
  - Identity passkeys, with only the Blazor template wired up.
  - Cookie auth returns 401/403 instead of redirects for API endpoints. This is a breaking change, good for an SPA ([aspnet/Announcements#525](https://github.com/aspnet/Announcements/issues/525)).
  - The `public partial class Program` source generator.
- **Earlier versions:**
  - .NET 8: `TimeProvider`, `AuthenticationSchemeOptions.TimeProvider`, and `RandomNumberGenerator.GetString`/`GetHexString`.
  - .NET 7: rate limiting middleware.
  - .NET Core 2.1: `FixedTimeEquals`.
- **NIST SP 800-63B-4 is final:** "07/31/25: SP 800-63B-4 (Final)", superseding SP 800-63B rev 3 ([CSRC](https://csrc.nist.gov/pubs/sp/800/63/b/4/final)). I cited the HTML edition at pages.nist.gov. Rev 4 forbids email for out-of-band authentication outright (§3.1.3.1). Read strictly, emailed sign-in codes don't meet any NIST AAL. OWASP's MFA CS treats email as a weak but possible factor ("Relies entirely on the security of the email account"). These are a conflict in strictness, not in facts. We accept the gap for now and plan passkeys.
- **Session timeouts conflict:** OWASP suggests 15–30 minute idle timeouts for low-risk apps, while NIST allows up to 30 days with no idle timeout at AAL1. I followed NIST, because every sign-in costs an email and a trip to the inbox.
- **Antiforgery storage:** Microsoft's antiforgery page recommends keeping the antiforgery token in local storage and sending it as a header. OWASP says not to keep _authentication_ tokens in web storage. The two don't conflict, because an antiforgery token isn't a credential, and the design above doesn't need either.
- **Auth0:** the pricing page doesn't say whether Free tenants can pick the EU locality. **Zitadel:** email code as the only factor is undocumented. **Clerk:** US-only per its own security page. **Keycloak:** no core email OTP or magic link found, though I only scanned part of the long release-notes page.
- **Rate limiter state is in memory per instance.** That's fine for one container, but a restart resets per-IP counters. The per-email counters live in the database for that reason.
- **Unverified:** whether `CloseOnAuthenticationExpiration` works with cookie tickets, and the minimal store interfaces `SignInManager` needs for passkeys over a custom `IUserStore<Account>`. Several Microsoft Learn pages carry `ai-usage: ai-assisted` metadata. Where it mattered, I checked claims against the `release/10.0` source.
